# Token 粗估（非实测）

本估算仅按技能说明、预期工具资料量和报告篇幅规划，没有运行排盘或生成样本报告来计数，没有调用任何付费模型。不同模型分词、会话历史和推理深度都会改变实际账单。

## 单次基础解读预算

先用中文内容约每字1～2 Token作为宽松规划假设；JSON字段、标点、英文、来源ID也计入输入。此比例是规划假设，不是模型的固定分词规则。

| 构成 | 规划范围 |
| --- | --- |
| 技能说明、必要参考指引和用户输入 | 2000～4500 Token |
| 命盘及关系事实 | 2000～5000 Token |
| focused 古籍依据 | 约4000～18000 Token，随命中完整段落长短浮动 |
| 约1000～2000中文字的基础报告 | 约1500～4000输出 Token |
| 一次准备工具调用的规划、参数及其他包装 | 约500～1500 Token，不能代表宿主全部开销 |

因此基础解读可先按**约1万～3.5万 Token 的一份新增可见内容预算**规划；不是整条 Agent 会话的累计计费保证。默认最多每书2个完整段落、每书2400字符，主要用于限制喂给 AI 的古籍资料，不会把四书全文一次塞入对话。

纯代码计算排盘、本地关键词排序本身不调用语言模型，不直接消耗模型Token。若让AI读取排盘结果、决定下一步或解释结果，相关输入输出仍消耗Token。

## 全文复核与多轮

`--context full` 纳入《子平真诠》全文，正文与附注的篇幅由随包底本决定。本轮没有用实际输出计数，故**不提供一个伪精确的全文总数**。可按下式对用户准备发送的文本规划：

`输入资料Token ≈ 其中文字数量 × 1～2 + JSON/英文等其他文本Token`

正文若有3万中文字，仅该部分按这个假设就约3万～6万Token；如果有8万字则约8万～16万。这里3万和8万是计算示例，不是本项目底本的实测字数。

多轮工具调用可能反复发送已有上下文。譬如同一份1万Token资料在两次模型请求中都出现，累计输入可接近2万，缓存可能影响费用但不能当成没有Token。隐藏推理Token、宿主系统提示、历史聊天、重试、逐年详解和评分都不包含在上述基础预算内；本技能不默认追加付费模型调用。

## 节省方式

基础分析先用focused；用户要求全文口径时再用full。只加载当前需要的参考文件，查询单书时指定book。能由代码计算的字段不交给AI反复推算；补充某条依据时只读取相应source_id，不重新加载全部书籍。

## 明确请求的大运评分流程

大运评分只在明确请求时执行，不能沿用基础报告的1万～3.5万估计作为其总用量。该流程使用原局基线一次，加指定大运每步一次；单步十年至少2个生成阶段，前六步至少7个生成阶段。格式或引用修正还可能增加阶段请求。

可用规划公式：`累计输入约为各阶段实际送入的提示、事实、原文、原局基线之和；累计输出约为原局基线报告加逐运报告之和`。全文原文在不同阶段可能重复进入模型，历史会话和隐藏推理另计。

纯假设示例：每阶段输入2万Token、原局输出3000、大运每步输出5000，则单步约4.8万Token，六步约17.3万Token；这里仅用算式说明阶段数量的影响，不是对本程序实际输出的测量或上限，也没有为此生成命盘报告。

人民币费用需要知道实际使用平台与模型的输入、缓存、输出定价后才能估算，不能把一个Token数量直接换成统一金额。
