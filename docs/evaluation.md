# 分层评估方案

把错误分开定位：排盘、检索和生成各自有独立测试集与结果，不把一个总分混在一起。

## 第一层：排盘回归

位置：`tests/test_bazi.py`。使用固定输入和预期四柱做回归比较，覆盖节气交界、子时换日、闰月、夏令时，以及真太阳时公式、经度、时区和跨日边界。

已有边界样例用于回归；后续还应加入由项目维护者确认的真实验收样例，并记录公历/农历输入类型、出生时间、出生地、时区、真太阳时开关、子时换日规则、预期四柱及预期来源。已知八字反推生日并不总是唯一，回归样例应以“已知出生输入→预期四柱”为主。

## 第二层：原文检索

位置：`data/annotations/conditions.json`、`eval/retrieval_cases.json` 和 `tests/test_structured_retrieval.py`。

每条人工整理的条件记录都关联原文出处、精确引文、日主、月令、透干/藏干条件和标注状态。运行时先用这些条件筛选候选，再用报告栏目主题做向量排序。检索层只返回原文和出处，不调用大模型。

评估案例为每个命盘主题人工标出相关 `source_id`，对返回列表计算 Recall@k、Precision@k 和 MRR（倒数排名）。运行 `python evaluate_retrieval.py` 会实际调用 Chroma 条件检索和向量排序。当前只有一个临时样例，因此指标只验证评估链路能工作；不能代表全书检索质量。还要扩大并人工复核相关原文，不要把尚未审核的标注计为权威命理结论。

## 第三层：AI 引用审计

模型生成尚未接入。`citation_audit.py` 先提供机械检查：每个解读条目必须带引用，引用 ID 必须存在，引用的原文必须能在来源行中逐字找到。

这不能自动判定“引用是否支持解读”。接入模型后，每份报告还要由人按条目抽查：

- 说法是否被引用原文直接支持，还是模型自行推断；
- 模型是否把有条件的原文说成无条件结论；
- 是否漏掉会改变适用性的日主、月份、透干等条件；
- 引文和出处是否准确，是否把多条古籍内容拼成原文没有的结论。

每条人工审核记录应保存模型版本、提示词版本、输入命盘、检索结果、生成报告、引用通过/不通过及原因。这样 RAG 检索错误和模型忠实度错误可以分开追查。

## 运行自动化测试

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
```

排盘、检索逻辑和引用格式分别有测试文件。测试通过表示这些已知回归用例通过，不代表所有古籍条件已整理，也不代表命理分析结论已获验证。
